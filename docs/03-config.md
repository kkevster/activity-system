# 03-config.md
## 配置管理方案

### 1. 主要配置项识别

| 配置项名称 | 说明 | 存放位置 |
|------------|------|----------|
| README.md | 项目说明与协作约定 | 项目根目录 |
| 01-wbs.md | 工作分解结构文档 | docs/ |
| 02-schedule.md | 简化进度计划 | docs/ |
| 03-config.md | 配置管理文档（本文件） | docs/ |
| 05-summary-report.md | 实验总结报告 | docs/ |
| conflict.md | 冲突模拟文件 | docs/ |
| 源代码/示例文件 | 功能实现代码 | src/ |

### 2. 分支策略

| 分支名称 | 用途 | 保护规则 |
|----------|------|----------|
| main | 存放最终交付物，所有成果汇总至此 | ✅ 受保护，禁止直接 push |
| dev | 日常开发与集成分支 | ❌ 不保护 |
| feature/xxx | 单个功能开发（如 feature/wbs、feature/schedule） | ❌ 不保护 |
| conflict-branch | 制造冲突用的临时分支 | ❌ 不保护 |

### 3. 提交规则

- **提交人名称**：必须设置为本人姓名拼音全称（如 `zhangsan`、`liminghao`）^[1]^
- **Commit Message 格式**：`类型: 描述`，例如 `feat: 添加配置管理文档`
- **提交频率**：每个任务完成后立即提交

### 4. 合并规则

| 合并类型 | 规则 | 责任人 |
|----------|------|--------|
| feature → dev | 完成开发后合并，需至少1人 review | 配置管理员 |
| dev → main | 所有交付物完成后合并，需全体成员确认 | 项目经理 |
| 冲突解决 | 手工解决后再次提交，保留完整记录 | 当事人 |

### 5. 冲突处理预案

- 冲突场景：不少于2名成员在不同分支修改同一文件同一位置^[2]^
- 处理方式：`git status` 识别 → 手工编辑解决 → `git add` → `git commit` → 合并
- 单人成组：创建两个分支，分别修改同一位置，自行模拟冲突^[3]^
